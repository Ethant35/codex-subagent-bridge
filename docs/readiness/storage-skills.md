## Compatibility and recovery

The released v1.0.0 JSON records remain readable. Its SQLite scheduler schema has `user_version=0`; first acquire adds or validates the existing `slots` table and commits `user_version=1` inside the same immediate transaction. A version greater than 1 is rejected without changing the file. The existing record layout remains unchanged.

`Store.list()` returns at most 100 records by default. Callers can pass `{limit, before}` for stable newest-first pages, with an exclusive cursor containing the previous page's `createdAt` and `id`. The maximum page size is 1000. Every page still validates all record files before returning, so corruption cannot hide outside the requested page; this also means repeated cursor pages rescan the directory. Persisted tasks are validated against the same task schema used for new requests. Run records are opened nonblocking and checked as private regular files, so a FIFO cannot hang a listing or inspection call.

Scheduler slot rows are now inserted before the transaction commits. The two-slot bound and release/reuse behavior are covered by a positive test and the CB-11 lifecycle test.

Before making a backup or restoring it, stop every CPB process that uses the state directory. Copy or restore the complete state directory as one unit while stopped, preserving private file and directory modes. Include `runs/`, `scheduler.sqlite`, and any SQLite journal or WAL sidecars present. Do not copy only the scheduler database while a process is active, and do not delete or edit individual corrupt run records to make listing succeed. Test a backup by pointing CPB at an isolated copy and running `cpb runs`; restore by replacing the whole state directory while CPB is stopped. v1.0.0 upgrade compatibility is covered by the checked-in released-code fixture; the fixture is not a user backup.

## Source checks

- Node's versioned v22.13.0 `node:sqlite` documentation was checked for `DatabaseSync` behavior and error handling: [Node.js v22.13.0 SQLite API](https://nodejs.org/download/release/v22.13.0/docs/api/sqlite.html).
- SQLite's primary result-code documentation was checked for `BUSY`, `LOCKED`, `CORRUPT`, and `NOTADB`: [SQLite result codes](https://www.sqlite.org/rescode.html).
- SQLite's `busy_timeout` and locking documentation informed the lock classification and real contention test: [PRAGMA documentation](https://www.sqlite.org/pragma.html#busy_timeout), [locking](https://www.sqlite.org/lockingv3.html).
- Apple's `fsync(2)` documentation was checked for directory-descriptor support limits. This machine accepted directory `fsync`; the implementation ignores only known unsupported-directory errors and keeps `EIO` visible: [Apple fsync(2)](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/fsync.2.html).

## Limits

The process identifier can be reused by the operating system. Store recovery checks whether the PID currently exists, but it cannot prove that the process still owns a particular run. Recovery never kills a PID. Storage behavior has been verified on this macOS arm64 / Node 22 environment only. No cross-platform guarantee is made here.
